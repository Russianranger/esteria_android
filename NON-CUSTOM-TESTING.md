## One preparation and play session

1. After v6 is published, install its signed ARM64 APK over the existing `io.github.russianranger.esteria.stock` app. The persistent certificate is unchanged. Preserve existing app data, completed import, setup state and saves. Check the release's `SHA256SUMS`, `release.json` and signing receipt for the exact APK/source identity.
2. Use the completed client import already shown by the app. Only if this is a fresh installation or no import ever completed, choose **Import client folder** or **Import client ZIP** and provide one complete ChromieCraft 3.3.5a build 12340 client. Select the root containing `Wow.exe` beside `Data`; keep normal MPQs inside `Data`, and locale/speech/locale-patch MPQs inside `Data/<installed-locale>`. Do not move archives next to `Wow.exe` or rebuild the ZIP. Folder import avoids ZIP staging. A normal enclosing client folder and harmless sibling README/Apple ZIP metadata are supported; selecting `Data` alone requires choosing its parent.
3. Read the compatibility result and keep the installed locale unchanged. Missing or malformed essential data remains a real error. Inactive ancillary archives stay in the original import and can be excluded from the separate stock selection; do not remove every archive containing “patch.” No additional Esteria or HD archive is required for this stock milestone.
4. Choose **Prepare local runtime / world**. Leave the app active while admission and hashing progress, even when a large-file phase lasts many minutes. The app prepares its tools, checks/selects stock data, generates dbc/maps/vmaps/mmaps/Cameras and graphics shaders, then initializes its local database when needed. No pre-extracted world download or manual MySQL setup is required. Keep adequate disk space for client/world/shader/database outputs; fresh database setup separately reserves 4 GiB of free storage.
5. If the app reports a memory pause, allow Android memory to recover and retry preparation. Completed phases are reused when their source/helper identities match. Stop remains available; allow owned child cleanup to finish. Preserve the existing import and saves. If Android closes the app, follow the support-export instructions below before another attempt.
6. After preparation succeeds, choose **Start local game** and allow database/auth/world readiness and graphical initialization to finish. Use the app's managed local login; do not enter ChromieCraft credentials or connect to a public realm. Create an ordinary **Human Warrior**, enter its stock starting area and confirm the world renders.
7. Check walking, turning, camera look/pan and basic object/NPC interactions using touch and the built-in controller. Note the exact stage of any failure: launcher preparation, login, character creation or world.
8. Exit the client normally and wait for **Local session stopped**. Start again with the same character and verify appearance, location and progress. After initial setup, enable airplane mode and disable Wi-Fi, then repeat startup/world entry, movement, clean stop and relaunch. Gameplay must remain local and offline.

## If preparation stops or Android closes the app

Reopen the app and **Export support bundle before another preparation attempt**. Do not clear data or reimport. Include the whole ZIP, the last displayed phase and whether Stop or Android caused the interruption. Keep `status.txt` and `launcher.log` together with any included fixed stock/data/shader/installation logs.

The new `preparation.last.*` fields retain the last admission/child phase, parent memory/headroom and limited child RSS/PSS coverage. `import.last.*` still describes the completed import. Android exit history records its reported reason and sampling limits. Clean-cache advice acceptance is not a count of pages actually reclaimed; child observations do not prove whole-guest memory coverage. Invalid retained log roles are excluded individually while other strictly validated fixed roles remain exportable. Bundles exclude databases, credentials and client assets.

The two v4 reports contain three unique Android `LOW_MEMORY` exits during preparation, but missing helper logs did not identify the exact child or allocation. Host fixtures and build success do not prove those owner exits are eliminated. V5 pause/retry handling preserves completed state and avoids caching a transient memory pause as bad client content. A forced termination is never reported as a successful character save.
