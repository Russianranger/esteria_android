# Transactional server data preparation

`runtime/server_data_generation.py` composes the actual ordered map/DBC/camera
extractor, ordered raw-vmap extractor, original vmap assembler and original mmap
generator. It requires a verified tool selection from application providers;
user client content cannot choose executable paths or compiler/configuration
inputs. The two ordered readers must return the exact capability contract.
Navigation uses the original7888-byte source configuration, relative dataDir and
one worker by default (two maximum). No shell or download is used.

Inputs are one completed build12340 import, its ancestry/journals and the exact
client471/serverf35 tools. The supported classical provider profile derives
from the reconstructed reader. Cached provider projections avoid hashing MPQs
again during a retry. Each actual reader independently validates its input pins.
Retail/Forever/streaming/alternate installation roots remain explicit unsupported
setup inputs until their separate complete local preparation is implemented.

Four phase completions retain hashed outputs. An interrupted raw vector phase
gets a different private directory on retry; its dirty Buildings directory is
never handed to the assembler. Completed phases are verified before reuse. The
assembler reads its completed raw input; navigation uses private map/vmap links
with a bounded-copy fallback when Android denies hard links. All inputs and active
generations remain separate. Failed/interrupted phase directories are retained
for diagnosis; automatic garbage collection and tile-level mmap resume are not
implemented yet. A failed navigation phase restarts that phase.

The helper reserves Linux process-group identity until cleanup, checks its
deadline/cancellation in both output loops and retains bounded head/tail logs.
The future Android owner must also retain the complete PRoot process/lease until
confirmed termination; this helper alone does not implement Android lifecycle.

Before an atomic current-pointer switch, the original bounded data preflight
checks every recognized file: WDBC lengths/continuations, MAPS9/build12340 chunk
bounds, VMAP_4.8, mmap20/Detour7 headers and MD20 cameras. Both entry counts and
directory depth are bounded, links/case collisions/unreadable subtrees fail, and
cached generations repeat this preflight. It verifies formats, not geographical
coverage, DBC row compatibility or custom overlays. Existing custom-server DBC
overlays/continuations still need a matched import layer before full Esteria play.

Nineteen focused host checks pass, including real Linux child output/cancellation
and synthetic transaction/recovery cases. No actual MPQ has been converted, no
world loaded and no Android execution is claimed. Ordered provider packaging,
Android operation/UI wiring and real12340 conversion remain next gates. The
stock extraction provider remains distinct from the ordered two-reader build.

The host command `python3 tools/check_assets.py --server-data <directory>` uses
the same `runtime/server_data_preflight.py` implementation; no validator copy is
maintained in the tools directory.
