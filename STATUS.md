## Stock v29 memory telemetry after a low-memory kill

**Owner v28 report.** The v28 game closed to the Android home screen while entering the world. The support ZIP contains no client or server error, and the server had reached readiness normally. Android's process-exit record for that moment is `LOW_MEMORY` at foreground importance, about 28 s after the client started. Android's low-memory killer stopped the app, and with it every process the app started.

The app's reading at client start shows 5.0 GB of memory available. Before the v27 session, which played for 411 s, it was 6.0 GB, and before v26 it was 7.0 GB. No v28 change runs during play apart from the GPU clock reads. The likeliest cause is therefore the memory that entering the world adds on top of the server stack and other apps. The bundle cannot show which process grew, because readings were stored only at a clean stop.

**Memory telemetry.** Each sample now records:

- memory available and swap;
- Android memory pressure (PSI), where readable;
- KGSL GPU page allocation;
- for each process role: resident memory (anonymous plus shared), swap and KGSL GPU memory.

Samples run every 3 s for the first two minutes after the client starts, then every 10 s. After every sample the memory readings are written synchronously to app storage. A session that ends without cleanup appears in the next support bundle as `game.interruptedSession.memory`, with the time of its last sample. A clean stop appears as `game.lastSession.memory`.

## Historical stock v27 PRoot acceleration and frame pipelining

**Owner v26 measurements.** The owner's v26 support ZIP covers 128 s of play at the 60 FPS cap. The PRoot tracers used 126.5% of one core on average, more than any other role. The Wine client used 61.8%, the worldserver 54.2%, the frame helper 33.8% and Xtigervnc 24.7%. The Adreno 740 averaged 10% busy. The hottest readable zones were `socd` at 73.0 °C and CPU zones at up to 70.0 °C. Android did not apply the requested sustained performance mode. The app posted 26.1 changed frames per second. Each frame took 14.7 ms to capture and 8.3 ms to post, and the two steps ran one after the other. [Measurements and plan](PERFORMANCE-PLAN.md).

**PRoot seccomp acceleration.** Every earlier build set `PROOT_NO_SECCOMP=1`, so PRoot stopped every guest system call. V27 lets PRoot install its seccomp filter for every PRoot process it starts, including setup and repair. With the filter, only the path, socket, process and SysV IPC calls that PRoot rewrites stop in the tracer, while futex waits, reads, writes, polls, sleeps and memory mappings run directly. PRoot falls back to full tracing by itself if the kernel refuses the filter. With `TRASC_PROOT_REPORT=1`, the pinned PRoot prints `TRASC PRoot: seccomp acceleration observed` to each component's stderr log when the filter is active. The launcher's **PRoot acceleration** setting defaults to on and applies at the next start. **Off** restores the v26 full tracing. The support bundle records the selection as `runtime.prootSeccompAcceleration.nextStart`. The Android 13 emulator probe now runs 13 guest launches. It compares accelerated and full-tracing output, requires the marker only in accelerated mode, and repeats forced and graceful ownership cleanup with acceleration on.

**Frame request pipelining.** At 30 and 60 FPS, Android sends the next frame request as soon as a changed frame's pixels have arrived, before it posts that frame. The guest helper captures the next frame while Android posts. The pinned protocol, guest helper and Wine cohort are unchanged. The helper still paces captures to 30 or 60 per second. An unchanged frame returns to Android-side pacing and idle backoff. At 24 FPS Android paces every request as before. The host probe checks the order of request and post and rejects duplicate requests, unknown flags and pipelining after unchanged or truncated replies. At 60 FPS, more delivered frames also mean more capture work, so heat comparisons use 30 FPS.

**Esync and zero-copy.** The pinned Wine 10.13 ARM64EC source has no esync, fsync or ntsync backend, so a setting alone cannot enable esync. fsync and ntsync also need newer kernels than Snapdragon 8 Gen 2 devices ship. The support bundle now records `device.kernelRelease`. The zero-copy design is in [PERFORMANCE-PLAN.md](PERFORMANCE-PLAN.md): the app allocates `AHardwareBuffer`s, Turnip renders into the imported dma-bufs through a guest Vulkan layer, and the buffers are presented with `ASurfaceTransaction`. It starts with a device probe and needs a new guest-bridge cohort. The same plan covers the esync port and running the server natively outside PRoot.

## Historical stock v26 thermal update for the working Thor installation

**Owner v25 heat baseline.** The owner's v25 support ZIP from the AYN Thor (Android 13) covers 170 s of play at the 30 FPS cap. Battery temperature rose from 25.0 to 27.0 °C and Android's thermal status stayed at 0 (none), so the owner's reading above 65 °C comes from an SoC sensor the v25 bundle did not record. The target is below 65 °C on that sensor.

**Server tick.** The worldserver now starts with `AC_MIN_WORLD_UPDATE_TIME=20` and `AC_MAP_UPDATE_INTERVAL=50` instead of the pinned 1 ms and 10 ms defaults. A host test ports the pinned `IniKeyToEnvVarKey` algorithm and checks it against the two names the v25 worldserver already read on device. As in v25, the saved configuration and its generation are unchanged, so no configuration fallback runs. TrinityCore 3.3.5 shipped 50 ms and 100 ms.

**Display pacing and sustained clocks.** The game surface requests its frame cap with `Surface.setFrameRate(cap, FIXED_SOURCE)`. The game window prefers the slowest display mode at the current resolution that is a whole multiple of the cap and never above the current mode, for example 60 Hz for 30 FPS on a 120 Hz panel. While the game is shown, the window also requests Android's sustained performance mode when supported. The gear menu has a **Sustained performance** toggle that applies immediately and defaults to on. Leaving the game clears both requests. Android treats both as requests; the bundle records the observed refresh rate.

**Thermal telemetry.** Sampling runs every 10 s instead of 30 s. A separate `game.lastSession.thermal` field records thermal headroom, observed display refresh, CPU policy frequencies and caps, Adreno busy, clock and temperature, the hottest readable thermal zones, and per-role CPU for every process the app can see, including PRoot tracers, Wine, Xtigervnc, the frame helper, worldserver and MySQL. It also records the display and sustained-mode requests and allowlisted graphics settings that the client saved to `Config.wtf`. Sources Android denies are reported as unavailable and not retried. No PIDs, process names, arguments or paths are exported. The existing observations field is unchanged.

**Frame helper copies.** Clang already vectorizes the Android-side swizzle (8 pixels per iteration), so v26 does not change it. The guest helper change that removes two full-frame copies is prepared as `patches/guest-bridges/0001-x11-frame-fewer-copies.patch` and is not applied. The helper is part of the published Wine cohort, and the APK build rejects a changed pinned source without a new cohort. On a host Xvfb, the patched helper produced identical wire output and used 26% less CPU for changed frames and 20% less for static frames. [Host evidence](runtime/evidence/non-custom-v26-frame-helper-copies.json) · [Adoption steps](patches/guest-bridges/README.md).
